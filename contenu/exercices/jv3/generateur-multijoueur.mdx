## Le contexte

Dans un jeu coopératif, les joueurs doivent réparer ensemble un générateur : chaque appui sur E ajoute 10 % de charge, et à 100 % une lumière s'allume pour tout le monde. Simple en solo. En multijoueur, c'est une autre histoire : chaque joueur a **sa propre copie** du monde, et seul le serveur a le droit de décider. Le serveur doit ensuite envoyer ses décisions aux clients : c'est la **réplication**.

Le développeur qui a écrit ce code n'a testé qu'en solo, ou en étant l'hôte. Tout semblait marcher.

## Ce que tu dois faire

**Pour tester :** dans la barre d'outils, menu des trois points à côté de Play, règle **Number of Players** sur 2 et **Net Mode** sur **Play As Listen Server**. Deux fenêtres s'ouvrent : l'hôte (serveur et joueur à la fois) et un client. Le Blueprint de ton personnage doit avoir `AJoueurReseau` comme parent (Class Settings › Parent Class), avec E branché sur **Reparer**.

**Ce que tu observes :**

- Quand l'**hôte** répare, son texte monte jusqu'à 100 %, mais la lumière ne s'allume jamais, ni chez lui ni chez le client. Chez le client, le texte reste à 0 %.
- Quand le **client** répare, seul le client voit son texte monter. L'hôte ne voit rien changer. Arrivé à 100 %, le client ne voit pas non plus la lumière.

**Ce qui est attendu :** que ce soit l'hôte ou le client qui répare, les deux fenêtres affichent la même charge, et la lumière s'allume chez les deux à 100 %.

Il y a **4 bugs**. Attention : ils se cachent les uns derrière les autres. En corriger un peut faire apparaître un nouveau symptôme, c'est normal. Garde l'Output Log ouvert, il te donnera deux indices précieux.

	for (TActorIterator<AGenerateur> It(GetWorld()); It; ++It)

		if (FVector::Dist(It->GetActorLocation(), GetActorLocation()) < DistanceReparation)

## C'est réussi quand…

- [ ] L'hôte répare : les deux fenêtres affichent la même charge.
- [ ] Le client répare : les deux fenêtres affichent la même charge.
- [ ] Les deux réparent en même temps : la charge monte deux fois plus vite, pareil chez les deux.
- [ ] À 100 %, la lumière s'allume dans les **deux** fenêtres, quel que soit le joueur qui a fini.
- [ ] L'Output Log n'affiche plus aucun avertissement `LogNet` au sujet du générateur.
- [ ] Avec 3 joueurs (Number of Players à 3), tout marche aussi pour le deuxième client.

## Si tu bloques

<Indice titre="Qui décide ?">
En réseau, une seule machine a l'autorité sur un acteur : le serveur. Une variable modifiée sur un client ne change **que** sur ce client. Pour qu'un client fasse changer quelque chose, il doit **demander** au serveur avec un RPC Server, puis le serveur modifie la variable, puis la réplication envoie la nouvelle valeur à tout le monde.
</Indice>

<Indice titre="Un acteur qui ne se réplique pas du tout">
Pour qu'un acteur envoie quoi que ce soit aux clients, il doit être marqué comme répliqué dans son constructeur. Sans ça, chaque machine a son générateur à elle, et chacune se croit le chef : c'est pour ça que le client voit sa charge monter, mais seulement chez lui.
</Indice>

<Indice titre="Lis l'Output Log">
Une fois le premier bug corrigé, deux messages devraient apparaître. Le premier dit qu'une propriété marquée `Replicated` n'a pas été enregistrée dans `GetLifetimeReplicatedProps`. Le second parle de « No owning connection » : un client ne peut appeler un RPC Server que sur un acteur qu'il **possède** (son personnage, son PlayerController, son PlayerState). Le générateur n'appartient à personne.
</Indice>

<Indice titre="La lumière de l'hôte">
`OnRep_Actif` est appelé automatiquement quand la nouvelle valeur **arrive** sur un client. Sur le serveur, la valeur ne « arrive » jamais : c'est lui qui l'a changée. En C++, il faut donc appeler soi-même `OnRep_Actif()` sur le serveur, juste après avoir changé `bActif`. (En Blueprint, les RepNotify sont appelés partout, d'où la surprise.)
</Indice>

void AGenerateur::GetLifetimeReplicatedProps(TArray<FLifetimeProperty>& OutLifetimeProps) const
{
	Super::GetLifetimeReplicatedProps(OutLifetimeProps);
	// Bug 2 : chaque propriété Replicated doit être enregistrée ici
	DOREPLIFETIME(AGenerateur, Charge);
	DOREPLIFETIME(AGenerateur, bActif);
}

void AGenerateur::AjouterCharge(float Quantite)
{
	// Sécurité : seul le serveur décide
	if (!HasAuthority() || bActif)
	{
		return;
	}

	Charge = FMath::Min(Charge + Quantite, ChargeMax);
	if (Charge >= ChargeMax)
	{
		bActif = true;
		// Bug 4 : en C++, le serveur ne reçoit pas son propre RepNotify
		OnRep_Actif();
	}
}

void AJoueurReseau::Reparer()
{
	if (AGenerateur* Generateur = TrouverGenerateur())
	{
		// Sur l'hôte, ce RPC s'exécute directement. Sur un client, il est envoyé au serveur.
		ServeurReparer(Generateur);
	}
}

void AJoueurReseau::ServeurReparer_Implementation(AGenerateur* Generateur)
{
	// Le serveur ne fait pas confiance au client : il revérifie la distance
	if (Generateur && FVector::Dist(Generateur->GetActorLocation(), GetActorLocation()) < DistanceReparation * 1.2f)
	{
		Generateur->AjouterCharge(QuantiteParAppui);
	}
}

**Pourquoi ça marche :**

**Bug 1, `bReplicates` oublié.** Un acteur qui ne se réplique pas existe en double, une copie par machine, sans aucun lien. Pire, chaque copie se croit chef (`HasAuthority()` est vrai partout) : le RPC Server du client s'exécutait donc... sur le client lui-même. D'où le symptôme « ça monte, mais seulement chez moi ».

**Bug 2, `Charge` jamais enregistrée.** Marquer une variable `Replicated` ne suffit pas : il faut aussi la déclarer dans `GetLifetimeReplicatedProps` avec `DOREPLIFETIME`. Sinon le moteur ne l'envoie jamais, et il l'écrit dans l'Output Log.

**Bug 3, le RPC au mauvais endroit.** Un client ne peut envoyer un RPC Server qu'à travers un acteur qu'il possède. Le générateur est posé dans le niveau, il n'appartient à aucun joueur : le moteur jette l'appel avec l'avertissement « No owning connection ». Le personnage, lui, appartient au PlayerController du client. On met donc le RPC sur le personnage, qui transmet au générateur côté serveur. C'est le même chemin que dans les vrais jeux : le joueur demande, le serveur vérifie, puis applique.

**Bug 4, le RepNotify oublié sur le serveur.** En C++, `OnRep_Actif` n'est appelé que sur les machines qui **reçoivent** la valeur. L'hôte l'a changée lui-même : sans appel manuel, sa lumière reste éteinte.

<Encadre type="retenir" titre="Le trajet d'une action en réseau">
Client : le joueur appuie sur E. Personnage : RPC Server. Serveur : vérifie, puis modifie une variable répliquée. Réplication : la nouvelle valeur part vers tous les clients. Clients : le RepNotify met à jour l'affichage. Sur le serveur : on appelle le RepNotify à la main.
</Encadre>

</Solution>

## Pour aller plus loin

- Le `Tick` qui réécrit le texte à chaque image est inutile : ajoute un `OnRep_Charge` qui met à jour le texte seulement quand la valeur change.
- Ajoute un son « générateur réparé » joué chez tout le monde avec un RPC `NetMulticast, Unreliable`, et compare avec ce que fait déjà le RepNotify : quand préférer l'un ou l'autre ?
- Ajoute un compteur de participation par joueur dans un `APlayerState` personnalisé, répliqué, et affiche « Merci Joueur 2 (60 %) » à la fin.
